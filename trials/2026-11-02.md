## SIGPIPE 141を成功へ写す段を明示

- 判定: **一部効果あり**
- 当てはめ先: claude -p や python3 -u の出力を >> ログ /2>&1 で受けている多数のcron（例: queue_consumer.py, monitor.py, [伏せ字] の cron.log 系、talmud/publish 系）。本文判定はしているが、途中でパイプ相手が閉じたときの141を「失敗」とみなす既存ロジックは無い
- やったこと:
  - snapshot.md から wrap_log を呼ぶ cron 5本（resim_safety_2300/0930, data_quality_probe, scan_health, tls_audit）を確認。全て末尾は `>> /path/log 2>&1`（ファイル追記）で、呼び出し側シェルに `| head`/`| tee`/`| awk` は無い。wrap_log 本体のソースは snapshot に含まれず読めないため、内部でパイプを使うかは不明。
  - /work/lab/sigpipe で F_GETPIPE_SZ=65536 を確認。
  - `python3 -u ... >> file 2>&1` に 1.28MB 吐かせても rc=0（ファイル追記は SIGPIPE が原理的に起きない）。
  - `python3 -u ... | head -1` を 100行/5000行/10000行/200000行で比較すると rc=1（Python既定の BrokenPipeError）。signal.signal(SIGPIPE, SIG_DFL) に差し替えると rc=141 を観測。
  - `yes | head -c 200000 | head -1` で PIPESTATUS=141 141 0 を観測。純シェルのパイプでは 141 が立つ。
  - 試作ラッパ wrap_fixed.sh を書き、3ケース検証: (A) SIGPIPE+本文あり→rc=0 に書換成功, (B) SIGPIPE+本文空→rc=141 のまま温存, (C) 正常終了→rc=0。全て期待通り。
- 観測: pipe buf=65536. '>>file 2>&1' 1.28MB 書込 rc=0. 'python3 -u | head -1' 既定 rc=1(BrokenPipeError), SIG_DFL後 rc=141. 'yes|head -c 200000|head -1' PIPESTATUS=141 141 0. wrap_fixed: Case1 outer_rc=0, Case2 outer_rc=141, Case3 outer_rc=0.
- 結論: SIGPIPE=141 は確かにパイプ経由で起きるが、スナップショットで見える cron は全て `>> file 2>&1` のファイル追記で、呼び出し側シェルからは 141 は原理的に起きない。また Python は既定で SIGPIPE を BrokenPipeError (exit=1) に変換するため、`python3 -u` の素の 141 は通常は観測されない（純シェル製のパイプ、または SIG_DFL 復帰後にのみ 141 になる）。したがって『141 を 0 に写す』修正は wrap_log 本体が内部でパイプを使っている場合に意味が出る防御であり、現状の呼び出し側パターンでは当面副作用は無いが実効も限定的。
- 本番に入れるなら: 要承認。~/ops/bin/wrap_log に『rc==141 かつ stdout 非空 → rc=0 扱い、空なら fail』の分岐を入れる案は妥当だが、適用前にまず wrap_log 本体を読んで『実際に内部パイプで 141 が立ちうるか』を確認したい。立たないなら no-op の防御コード、立つなら実効のある修正になる。段階適用は tls_audit など低頻度の cron から。戻しは wrap_log 1 ファイルの差し戻しのみ。
