  - Experiment B: owned.pid に『既に別コマンド(python3)に再利用された PID』を書いて stop_naive.sh を実行し、無関係の python3 プロセスを誤爆して殺せることを確認（PID再利用時の事故を再現）。
  - Experiment C: 同じ再利用シナリオで stop_safe.sh sleep を実行し、comm='python3' != expected='sleep' のため kill せず終了し、python3 が生存することを確認。
  - Experiment D（計画外の実観測）: pkill -f 'sleep 600' をデモスクリプト内から実行したところ、サブシェル自身まで巻き込まれて exit 144 で中断。snapshot:32 の『pkill で自分のシェルまで殺す』が偶発的に実演された。
- 観測: A: ps 出力 'foreign STILL running (good)' / 'owned gone (good)'。safe log: 'safe: killed pid=102 comm=sleep'。 B: 'naive: killed pid=119' → victim(python3) DEAD。 C: 'safe: refuse-kill pid=127 comm=python3 expected=sleep (PID reused)' → victim2 ALIVE。 D: pkill -f 'sleep 600' 実行後にスクリプトが exit 144 で中断、owned.pid に PID 144（自サブシェル）が残る副作用まで観測。
- 結論: owned.pid に自PIDを書いて停止側がそれだけを kill する作りは、同名の別プロセスを巻き込まないという点で lab 内で明確に効いた。さらに『owned.pid の PID が別コマンドに再利用されている』ケースでも ps -p PID -o comm= の 1 行照合を足せば誤爆を完全に防げる。おまけに pkill -f の広域マッチが呼び出し元シェルまで刈る挙動も偶発的に再現できて、owned.pid 方式の必然性が強まった。
- 本番に入れるなら: 本番適用は要承認。各 ensure*.sh / watchdog*.sh の起動部で `echo $! > "$STATE/owned.pid"` を 1 行足し、停止側は『owned.pid があれば kill -0 と comm 照合を通ったものだけを kill、無ければ従来の pgrep/pkill にフォールバック』の順にする。cron 本体には触らない。巻き戻しは追加した数行をコメントアウトし `find ~/*/state -name owned.pid -delete` で状態ファイルを消すだけ。既存の広域 kill は残したまま前段に追加する形なので、挙動が悪化しても即復旧できる。
