- やったこと:
  - snapshot.md で本番の3層構成(nginx FastCGI 7日・LiteSpeed・Cloudflare)とCF迂回の--resolve運用が既出であることを確認(snapshot.md:23-24)
  - /work/lab/cache_probe/ に python3 標準ライブラリだけで3層キャッシュのモックを作成 (mock_layer.py / _layer_multi.py)。CF=9003, LS=9002, nginx=9001 の3プロセスを起動
  - 各層ごとに別のレスポンスヘッダ名 (cf-cache-status / x-litespeed-cache / x-cache) と Age/X-Layer を返し、?nocache= または Cache-Control: no-cache で素通りする挙動を実装
  - 3シナリオを仕込んだ targets.txt を用意: (1) roadmap1000=CFだけ古い, (2) sat_english=LSが古い, (3) talmud=全層一致

  - diagnose.sh で md5 の一致パターンから『どの層が古いか』を1行で判定するロジックを実装し、3シナリオ全てで正答
- 観測: out.tsv より md5 (先頭8桁): roadmap1000 A=fda9ab06 B=346f2161 C=346f2161 → 診断『STALE: Cloudflare (A!=C, B==C)』 / sat_english A=ad72db69 B=d7eacfca C=ad72db69 → 『STALE: LiteSpeed/nginx (A==C, B!=C)』 / talmud A=B=C=d94ae3af → 『OK: all layers match』。層ごとのヘッダ名も分離 (CF経由ではcf-cache-status=HIT、LS直ではx-litespeed-cache=HIT)。3シナリオ3/3で層の特定が1行で成立
- 結論: A/B/C三叩きで本文md5の一致パターンから古い層を機械的に特定できることをラボで実証。層ごとに別名のヘッダ (cf-cache-status / x-litespeed-cache / x-cache) が付くので、md5が同じでもどの層がHITを返したかが同時に分かる。『直したのに直ってない』事象の切り分けコストが明確に下がる形になった。
- 本番に入れるなら: 本番適用は要承認。probe.sh/diagnose.sh を read-only で ~/ops/cache_probe/ に設置。GETのみ・パージ無し。targets.txt は公開済み記事3-5件に限定。weekly_audit に `cd ~/ops/cache_probe && bash probe.sh > out.tsv && bash diagnose.sh >> ~/ops/logs/cache_probe.tsv` を1行追加。本番では --resolve <domain>:443:<オリジンIP> を B 列に、A は通常のCloudflare経由、C は ?nocache=$RANDOM で実装し直す。戻す時は cron 1行削除とディレクトリrmで完結。アクセスログに自IPが残る点だけ留意。
