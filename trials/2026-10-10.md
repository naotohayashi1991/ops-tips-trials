  - ② /work/lab/key_audit/ に検証一式を構築: ダミーで ssh-keygen -t ed25519/-t rsa 計6鍵の authorized_keys.sample(コメント: alice[相手]-active, bob[相手], carol-deploy-2024, dave[相手], コメント無し, eve[相手]-ci)、及び journalctl 風書式の Accepted publickey ログ9件を作成。

  - sshd ログを正規表現で走査し、Accepted publickey の SHA256 フィンガープリントごとに最終使用日/使用回数を集計、CSV(lineno,fingerprint,comment,key_type,bits,last_used_30d,uses_30d,status)に出力。
  - エッジケースとして空ログも実行し、全鍵が STALE_never_in_30d に落ちることを確認(journald の保持期間が足りないと誤検知する落とし穴を実測)。

- 結論: authorized_keys の各行に対して『フィンガープリント・コメント・最終使用日・30日未使用か』を1枚のCSVで列挙する雛形は動いた。鍵本体を一切書き換えず読むだけで棚卸しできるので、週次 cron で回す案は現実的。ただし成否は journalctl の保持期間に強く依存し、デフォルトのままだと active な鍵まで『未使用』扱いになるので、本番投入前に journald の保持日数の確認が必須。

## 鮮度監視をperiod+graceで判定

- 判定: **一部効果あり**
- 当てはめ先: ops/mtime_watch/registry.csv（既にOK/LATE/UNMEASURED 3状態運用中）
- やったこと:
  - ①読み取り確認: snapshot.md では該当は L156 の cron 1行のみ (`*/15 * * * * /usr/bin/python3 ~/ops/mtime_watch/watch.py ~/ops/mtime_watch/registry.csv >> ~/ops/logs/mtime_watch.cron.log 2>&1`)。本物の registry.csv・watch.py・ログ本文はスナップショットに含まれないため、ここは1行の存在確認のみ。
  - ②lab 内で代用部品を構築: /work/lab/mtime_watch/{registry.csv, watch_old.py, watch_new.py, seed.sh} を作成。registry は watchdog(*/5,*/10,*/15) 19本 + daily 4本 + weekly 4本 の計27本。fakeroot のファイル mtime を seed.sh で固定時刻 (NOW=2026-10-10T22:30+09:00) 基準に埋め込み、9件 LATE + 2件 UNMEASURED になるシナリオにした。
  - watch_old.py = 既定ロジック: upper = period * 2 (graceDays 列は無視)。watch_new.py = period + grace: graceDays セル空なら grace=period(=既定で period*2 と同値)、値ありなら graceDays*1440 を加算。
  - 同じ CSV・同じ NOW で両方を実行し、state だけで diff を取って完全一致を確認: `diff <(awk '{print $1,$NF}' out_old.txt) <(awk '{print $1,$NF}' out_new.txt)` の出力は空。
  - 週次行の graceDays を 10 → 3 に書き換えた registry_weekly3.csv を watch_new.py に食わせ、新たな LATE が増える様子と原因行の特定可能性を観測。
- 観測: baseline (watch_old / watch_new どちらも): OK=16 LATE=9 UNMEASURED=2 で全行一致、state 列の diff 空。LATE 9行は ib_physics_wd, ielts_video_watcher, hard_wd, roadmap_wd, talmud_verify, daily_resim, daily_nishimiya, weekly_audit, weekly_outreach。UNMEASURED 2行は speaking_wd, weekly_dataquality。週次 graceDays=3 に詰めると OK=15 LATE=10 UNMEASURED=2、唯一変化したのは weekly_borderline (age=15000min, upper 24480→14400 で OK→LATE)。他26行は一切変化せず、追加 LATE の原因行は age/upper の差分から1行で特定可能。
- 結論: lab 内の代用データで検証した範囲では、period+grace 方式は『graceDays セル空=既定(周期×2)』として従来挙動を 100% 再現し、週次だけ grace を 3日に詰めると意図通り該当1行だけが LATE に反転した。CSV の1列追加で済み、既存の赤行判定を壊さないという主張は少なくとも設計レベルで妥当。ただし本物の registry.csv/watch.py/本番ログは今回の環境で読めなかったので、『本番の過去赤行9件＋2件 UNMEASURED と完全一致』の実データ照合はできていない。
- 本番に入れるなら: 要承認。手順: (1) 本番 registry.csv を取り、graceDays 列を手で埋める(週次=10 or 3、日次=3、*/5分や*/10分は空=既定)。(2) watch.py を lab の watch_new.py 相当(period+grace, 空セル→period 既定)に差し替え。(3) 旧スクリプトを並列実行してログの LATE 行集合が一致するか1cron周期(15分)観測。(4) 一致を確認したら切替。戻しは git で watch.py と registry.csv を1コミット前に戻すだけ。本番 cron は止めない。
