## 非対話CLIは stdin を閉じ、点検は read-only で

- 判定: **一部効果あり**
- 当てはめ先: claude -p / codex を使う [伏せ字], kronos-runner, 各工場（sat_vocab_factory, ib_math_factory 等）の watchdog。既往の『claude -p が終了コード0でも空・途中切れ』『codex が黙ってAPI課金に落ちた』の系統の無言ハング対策。
- やったこと:
  - snapshot.md を grep：claude -p / codex の起動行では </dev/null も -s read-only も使われていない（該当なし）ことを確認。cron の >/dev/null 2>&1 はいずれも stdout/stderr 側で、stdin は閉じていない。
  - /work/lab/stdin_probe に run_codex.sh と run_claude.sh を作成し、同一プロンプトで『stdin open』『stdin closed（</dev/null）』を対で計測。timeout 45s でハング検知。
  - claude -p --disallowedTools 'Bash Edit Write NotebookEdit' -p 'Reply with exactly: hello' を open/closed で実行。
  - codex exec -s read-only --skip-git-repo-check 'Reply ...' を open/closed で実行（この lab は未認証なので LLM 側は 401 で終わるが、プロセス挙動は比較可能）。
  - read-only の実効性を直接確認するため、codex sandbox -- bash -c 'echo X > sentinel.txt' を実行し、無サンドボックスでの書き込みと比較。
- 観測: claude: open rc=0 5s out=6B / closed rc=0 6s out=6B（本文はどちらも 'hello\n'、差分なし）。codex: open rc=1 15s / closed rc=1 15s（両方とも 401 Unauthorized で終了、hang せず挙動一致）。codex sandbox 下では書き込みが『Read-only file system』で拒否されDENIED、無サンドボックスでは同じコマンドが OK で sentinel 更新。sandbox 下では外部 HTTPS も http_code=000（遮断）。
- 結論: </dev/null で stdin を閉じる変更は、少なくとも通常経路で遅延も出力減もなく『無害で安い』ことが確認できた（claude 側で出力バイト数・終了コード完全一致）。codex の -s read-only（≒ codex sandbox の read-only プロファイル）は実際に書き込みを明示エラーで止めるので、点検系の『誤って生成物を触る』事故を物理的に防げる本物の対策。ただし20分の lab 中に無言ハング自体は再現できず、『ハング減少』は観測としては示せていない（頻度が低い現象のため）。
- 本番に入れるなら: 本番導入は要承認。方針：(1) ~/ops/bin/call_llm_readonly.sh を新設し、内部で '</dev/null' + 'codex exec -s read-only' もしくは 'claude -p --disallowedTools "Bash Edit Write NotebookEdit" --permission-mode plan' を呼ぶラッパーに統一。(2) 置換対象は点検系（scan_health / zombie_watch / postverify / mtime_watch）に限定し、生成系（kronos-runner、各 *_factory watchdog、[伏せ字] 本体）は現状維持。(3) 置換は cron 1 行ずつ段階投入してログ比較。(4) 戻しは git -C ~/ops revert、または cron 行の # コメントアウト解除で即復旧。
