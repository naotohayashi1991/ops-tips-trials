## プロセス置換のPIDは直後に捕捉

- 判定: **効果あり**
- 当てはめ先: sat_english_factory/build_*_books*.sh や kronos-runner の集約バッチ、ops/postverify/run_cron.sh など、<(...) で複数の生成系をぶつけてから diff/merge している可能性のある箇所。片側が静かに落ちると PIPESTATUS だけでは捕まらずログだけ減って通ってしまう。
- やったこと:
  - snapshot.md を読み、対象として挙がった sat_english_factory / kronos-runner / ops/postverify のスクリプト本体は含まれていないことを確認（crontab 行の呼び出しだけで、<(...) を使っているかは判定不能）。bash --version=5.2.21。
  - /work/lab/proc_sub_wait に、終了コードを引数で返す fail.sh と、固定の出力を吐いてから任意の rc で落ちる emit_then_fail.sh を作成。
  - ケースA（素朴 diff <(a) <(b)）、ケースB（cmd <(a) <(b) & $! 捕捉）、ケースC（exec N< <(cmd) で置換ごとに直後 $! を配列化→個別 wait）の3つを実装し、片方 exit=7 で挙動を比較。
  - 最も危険なパターン『両方の出力は一致するが片側が rc=7 で落ちている』を emit_then_fail.sh で再現し、ケースA（naive）とケースC（per-sub capture）を10回連続で走らせて検出率を測定。
  - 別途、`cmd <(a) <(b)` の直後に見える $! が最後の置換のみを指すことも、wait で rc=7 が返る様子で観測。
- 観測: ケースA (naive diff): diff_rc=0, PIPESTATUS=0 ← 片側 exit=7 が完全に見えない。ケースC (per-sub): diff_rc=0 でも pid_B の rc_B=7 を捕捉、ラッパーは exit 20 (LEG_FAILED) で終了。stress10 の集計: naive=detected 0/10, missed 10/10 ； per-sub=detected 10/10, missed 0/10（成功基準の『10回連続で誤判定0』を満たす）。また bash 5.2 で `cmd <(a) <(b)` 直後の $! は最後の置換の PID のみを保持することを wait rc=7 で確認。
- 結論: 知見は再現できた。置換ごとに `exec N< <(...); pid=$!` の形で直後に PID を取り、最後にそれぞれを個別 wait するだけで、diff/PIPESTATUS では見えない『片側の静かな失敗』を 10/10 で検出できた。本番側については snapshot.md にスクリプト本体が無く、現状これらのパターンが使われているかどうかは判定できなかったので、適用前に本番で `grep -nE '<\(' ...` の確認が必要。
- 本番に入れるなら: 本番でそのまま入れる前に、まず読み取りだけ: `grep -RnE '<\(' ~/sat_english_factory ~/kronos-runner ~/ops 2>/dev/null` で該当箇所を列挙する（snapshot には本体が無く未確認）。該当があれば、置換ごとに `exec N< <(...); pA=$!` の形へ順次書き換え（または pid 配列 + for ループ wait）し、wrap_log 側で [pid rc] の2列を落とす。各ファイルは `.bak` を取って git diff / cp .bak 復元が効くようにする。全てユーザー承認後に実施。

## exit 141はSIGPIPEで異常でない場合

- 判定: **効果あり**
- 当てはめ先: scan_health, ops/postverify, sessions_registry/build_registry.sh、x_poster.py 周辺のシェル前処理など head/jq/sort -u | head を使っている判定箇所。『成否は出力の中身で判定』の方針に、PIPESTATUS解釈のレイヤを足せる。
- やったこと:
  - snapshot.md を grep して wrap_log/scan_health/postverify/build_registry.sh の cron 行は見つけたが、スクリプト本体やログは snapshot に無く『①読み取り確認』の head/jq パイプ箇所の直接引用はできなかった旨を明記
  - /work/lab/sigpipe_check/ で intended-141 と abnormal-141 を実物のパイプで再現: `seq | awk | head` と `yes | awk NR==5{exit 7} | jq | head`
  - pipefail なしでは rc=0、pipefail ありでは intended=rc=141 / abnormal=rc=7 となる挙動を観測し、終了コード単独では区別不能・PIPESTATUS 配列を見る必要があることを確認
  - judge_pipestatus(ends_with_head, pipe[]) を bash で実装: 末尾が head の打ち切り設計のときだけ、head より手前の位置の 141 を intended として許し、それ以外の非ゼロは全部 abnormal 扱い
  - intended-141 10件 + abnormal-141/その他エラー 10件 の計20件を testcases.tsv に用意し、judge で 20/20 PASS。素朴判定（PIPESTATUS に非ゼロがあれば異常）でも同じ入力を評価し、false_alarm=10 / miss=0 と比較
- 観測: 観測: `seq | awk | head -5` → PIPESTATUS=141 141 0, pipefail下 rc=141 (intended)。`yes | awk 'NR==5{exit 7}' | jq | head -3` → PIPESTATUS=141 7 0 0, pipefail下 rc=7 (abnormal)。judge_pipestatus でのテスト結果: PASS=20 FAIL=0。素朴判定の誤分類: misclass=10 false_alarm=10 miss=0（intended-141 を全部異常扱いしてしまう）。judge 導入後 false_alarm=0 miss=0。
- 結論: 計画どおり効果あり。head 打ち切り設計での 141 は PIPESTATUS 配列の位置と『末尾が head か』の2情報で intended と abnormal を安全に分けられる。素朴判定だと intended-141 を 10/10 すべて異常扱いしてしまう（狼少年化）が、judge_pipestatus を挟めば 20/20 で誤分類ゼロ、本物の下流落ちも拾える。
- 本番に入れるなら: 本番の ops/bin/wrap_log 側に判定レイヤを足す（要承認）: 対象コマンドが『末尾 | head -N』で終わる設計の場合は PIPESTATUS[0..n-2]==141 を intended として許容、それ以外の非ゼロと PIPESTATUS[n-1] の非ゼロは異常。該当箇所（scan_health / postverify / build_registry.sh / x_poster.py 周辺の head/jq/sort -u | head）にコメントで『intended SIGPIPE』を明記。戻しは判定条件の diff を戻すだけ。導入前に本番ログで直近の 141 行を人目で確認し、intended か abnormal かの実分布を 1 日ぶん見て再チェックしたい（snapshot には実ログが無く未検証）。
